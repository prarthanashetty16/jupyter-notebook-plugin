## Candidate model gaps (proposals only; ranked by costly cells affected; any change needs a fresh split and a new freeze)

Measured costly cells: 3 (the two `read_csv` cells and the killed `fillna` / `astype` cell). Static counts from the Phase 4e
coverage study of the same notebooks are given as context, not as measurements.

1. **Several frames loaded in one cell (2 of 2 measured costly cells).** The cell's expected RAM is the MAX of its operations'
   expected values (`nexus.risk.combine`), but when every result stays bound to its own name the peak is close to their SUM:
   bias 0.56 on both cells. A combination that sums the expected values of independent, retained results (and keeps the max for
   chained temporaries) is the hypothesis.
2. **The cell's `high` is the sum of Tier 0 highs (2 of 2).** 17-29 GiB for cells that used 3.8 GiB: every such cell is WARN on a
   laptop (2 false alarms at the free-RAM limit). Tied to gap 3 and to the known R2 failure of read_csv under policy B.
3. **`read_csv` Tier 1 refuses any call with `sep=` or `dtype=` (2 of 2 measured cells; all 7 input files of the two Amazon
   notebooks are TSVs; how many of the 13 statically detected `read_csv` cells pass such options was not counted).** `ReadCsvModel` only accepts `filepath_or_buffer`, `encoding`, `low_memory` at Tier 1, so tab-separated reads stay at
   Tier 0 (bytes per field unknown, 2..24). Supporting `sep` and an explicit `dtype` in the sniffed sample is the hypothesis.
4. **Operations without a model on large frames (1 measured cell, killed: `fillna` / `astype` chain; statically `copy` 110 cells,
   `fillna` 29, `apply` 34, `explode` 22).** These are detection-only and UNKNOWN; on these notebooks they are where the memory
   goes after loading.
5. **The extension's default is Tier 0** (`%load_ext nexus` builds `Pipeline()`, tier 0): a user never gets Tier 1 or the
   controller without configuring it. A UX / default decision, outside the frozen files.

## Harness limits and threats to validity

* **Too little evidence:** 2 valid RAM points and 1 valid time point, all `read_csv`; every verdict is INCONCLUSIVE.
* The machine: 5.5-5.7 GiB free of 16 GiB (other programs running); the 70%-of-free cap stopped both notebooks while loading.
  A run with more free RAM (closing other programs) or on the Linux VM would get past the loading cells.
* Sample: 3 notebooks from one author, ML-heavy, one dataset; one was not runnable (Colab-only).
* pyarrow absent: the notebooks' parquet steps (amazon_ml_solution) would have failed further on; xgboost etc. were installed
  for this run.
* Windows' peak counter cannot be reset: in a longer run most cells after the first large allocation would be censored.
* One run per cell; cold file reads; the kernel is an IPython `InteractiveShell` in a spawned process, not an ipykernel.
